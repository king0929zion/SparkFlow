# SparkFlow 架构说明

## 设计目标

SparkFlow 的核心约束只有三个：

1. `main` 是唯一分支和唯一事实来源。
2. 所有运行模式共用同一套配置解析、Cookie 标准化和自动化核心。
3. 配置错误必须在浏览器启动前失败，页面兼容性必须在正式发送前用 smoke 验证。

## 运行链路

```text
GitHub Environment / .env
          │
          ▼
utils.config
  ├─ RuntimeConfig
  ├─ AccountTask
  ├─ Cookie normalize
  └─ strict validation
          │
          ▼
core.runtime
  ├─ send
  ├─ smoke
  └─ run-status.json
          │
          ▼
core.tasks
          │
          ▼
Playwright -> https://www.douyin.com/chat
```

`main.py` 只是 CLI 适配层，不再复制配置校验或状态记录逻辑。

## 配置层

`utils/config.py` 同时服务于本地运行、GitHub Actions、Web 控制中心生成结果和自动化核心。

它负责：

- 验证 `MATCH_MODE`、超时、重试次数、日志级别。
- 验证 `TASKS` 是否是非空账号数组。
- 验证每个账号是否有唯一 `unique_id` 和至少一个目标好友。
- 定位 `COOKIES_<UNIQUE_ID>`。
- 将 Cookie-Editor JSON 转换为 Playwright cookie schema。
- 兼容 `domain + path` 与 `url` 两种 Cookie 表达形式。

`get_config()` 和 `get_userData()` 仍保留原来的 dict 接口，以避免自动化核心产生无意义的大规模改写。

## 运行层

`core/runtime.py` 统一管理：

- `RunMode.SEND`
- `RunMode.SMOKE`
- 旧 `SPARKFLOW_SMOKE_TEST` 兼容
- `SPARKFLOW_MODE`
- `run-status.json`
- 异常状态记录

这样 GitHub Actions、本地 CLI 和后续其他调用方不需要各自实现一套运行模式判断。

## GitHub Actions

### `schedule.yml`

唯一业务工作流。手动运行选择 `smoke` 或 `send`；定时运行固定先 smoke，再 send。

### `ci.yml`

每次 push / pull request 到 `main` 时执行：

- Python compileall
- unittest

这些测试不依赖 Playwright 浏览器，因此用于快速发现配置层、运行层和仓库结构回归。

### `branch-policy.yml`

仓库约束为 main-only。策略工作流会：

- 在策略首次提交时扫描并删除所有非 `main` 分支。
- 在以后创建新分支时再次运行清理。
- 删除后重新读取分支列表，若不是只剩 `main` 就直接失败。

## 为什么没有重写 `core/tasks.py`

`core/tasks.py` 保存的是最容易受抖音页面变化影响的选择器、聊天列表定位和发送流程。此次重构把外围重复逻辑收拢，但刻意保留已经验证过的 Web Chat 自动化核心，减少架构整理引入页面行为回归的风险。

后续若要继续拆分，建议按以下边界逐步迁移，并始终先通过 smoke：

```text
core/tasks.py
  -> chat/session.py
  -> chat/search.py
  -> chat/conversation.py
  -> chat/sender.py
```
